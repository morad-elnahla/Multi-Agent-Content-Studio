Access Control

TWEET 01 / 05

An audit of Swig found that sign_v1 does not limit which instructions can target accounts, allowing limited-permission users to run unauthorized actions.

TWEET 02 / 05

The permission check only fires when a transaction alters an account balance, so operations that only change control pass unchecked.

TWEET 03 / 05

For example, a user with a TokenLimit role for mint [0;32] and amount 1 can issue SetAuthority on a token account; the balance stays the same, the check passes, and ownership transfers.

TWEET 04 / 05

The same gap can be exploited on stake accounts or any account where authority or lockup parameters can be altered without affecting balances, compromising asset control.

TWEET 05 / 05

Recommendation: restrict allowed instruction types per account type and require explicit verification for control-changing actions. Consider a review. [SS-03699]

THREAD 025 tweets in this thread

Oracle Manipulation

TWEET 01 / 05

An audit of Hylo discovered that its price oracle accepts any account sharing the same feed ID, not just the official Pyth feed.

TWEET 02 / 05

The program checks only the feed ID, so non-canonical accounts pass the verification step and become trusted sources for price data.

TWEET 03 / 05

An attacker can create a PriceUpdateV2 account, submit a historical price within the 60 s window, and have the contract use that older value.

TWEET 04 / 05

This allows manipulation of any Hylo logic that relies on the oracle price, even though publish and update timestamps are otherwise validated.

TWEET 05 / 05

Fix: enforce a single canonical feed account managed by Pyth, or use a personal persistent account you control for updates. [SS-03738]

THREAD 035 tweets in this thread

Slippage Protection

TWEET 01 / 05

An audit of Hylo found its swap instruction lacks slippage protection. It calculates rates using oracle prices, token supplies and protocol state.

TWEET 02 / 05

Because those inputs can change between submission and execution, a front-runner can alter the oracle price or token supply, resulting in a worse rate for the user.

TWEET 03 / 05

The root cause is that the swap instruction does not enforce any user-specified slippage bound.

TWEET 04 / 05

Without a slippage bound, the transaction may complete at any rate, exposing the caller to potentially unfavorable outcomes.

TWEET 05 / 05

Add a slippage check: require a minimum acceptable output and revert if the actual result is lower. [SS-03740]
